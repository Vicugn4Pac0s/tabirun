# 承認付き開発ワークフロー

リポジトリの `AGENTS.md` を先に読み、その規約をこの手順より優先する。調査と計画を実装から分離し、承認された範囲だけを変更する。

## 1. タスクを理解する

1. 要求、完了条件、非対象範囲を整理する。
2. コードから合理的に判断できる事項は調査して前提として明記する。
3. 方針を左右する重大な不明点だけを質問する。
4. 初回依頼に「承認不要」「そのまま実装してよい」など、承認待ちを省略する明示指示があるか確認する。

## 2. 承認前に調査する

承認前は読み取り専用操作に限定する。

1. `git status --short --branch` でブランチと既存変更を確認する。
2. ルートから対象ディレクトリまでの指示ファイルを確認する。
3. `README`、`package.json`、設定、CI、関連ソース、テスト、ドキュメントを読む。
4. `rg` と `rg --files` を優先し、呼び出し元、依存先、類似実装、テストを追跡する。
5. UI、ロジック、データ取得、API、DBの責務と依存方向を把握する。
6. 秘密情報は値を読まず、ファイルや変数名の存在確認に留める。

承認前はファイル変更、生成物作成、キャッシュを書き得る検証、branch操作、依存操作、migration、commit、push、PR作成を行わない。

## 3. 実装計画を提示する

`references/implementation-plan-template.md` を読み、全項目を埋める。変更予定ファイルは既存と新規に分け、検証コマンドと外部操作も具体化する。

推奨案を先に示し、少なくとも1つの代替案と不採用理由を添える。既存変更との競合、認証、環境変数、migration、互換性、UI回帰などのリスクを明記する。

計画末尾で明示的な承認を求め、そのターンでは実装しない。

## 4. 明示的な承認を確認する

次のいずれかを承認として扱う。

- 提示した計画に対し、実装を進める意思が明確な返答を受けた。
- 初回依頼で、承認待ちが不要で直ちに実装してよいと明示された。

曖昧な返答は承認と推測しない。承認後に変更範囲、依存追加、migration、外部操作などが計画から重大に変わる場合は、更新計画を示して再承認を待つ。

本番変更とデプロイは、通常の実装承認に含めず、常に別途明示的な承認を得る。

## 5. 作業ブランチを準備する

1. `git status --short --branch` を再実行する。
2. ユーザーの未コミット変更を見つけた場合は、上書き、破棄、自動stashをしない。
3. 計画で承認された名前で、原則として最新の確認済みベースから作業ブランチを作る。
4. 命名規約がなければ `<type>/<short-kebab-summary>` を使う。
5. 既存の適切な作業ブランチを継続する必要がある場合は、その理由を報告する。

## 6. 小さく実装する

1. 既存の設計、命名、責務分離、依存方向を維持する。
2. UI、ロジック、データ取得を分離し、Reactのロジックはhooksへ置く。
3. API呼び出しをコンポーネントへ直接書かず、mutation成功時は関連データをinvalidateする。
4. `any` を使わず、外部入力と永続化データをZodなどで検証する。
5. 機能変更と無関係な整形やリファクタリングを混ぜない。
6. 新しい外部依存やmigrationが必要になったら、計画にない限り停止して承認を得る。
7. 変更に対応する正常系、境界値、異常系、回帰テストを追加または更新する。

## 7. 変更に応じて検証する

リポジトリの `package.json` を正とし、変更範囲に比例した検証を行う。

- TypeScript/React/サーバー変更: `npm run format:check`、`npm run lint`、`npm run typecheck`、`npm run test:run`、`npm run build`
- UI/Story変更: 上記に加えて `npm run test:storybook`、必要なら `npm run build-storybook`
- DB変更: schemaと生成migrationを確認する。`db:generate` は計画済みの場合だけ実行し、`db:migrate` と `db:push` は対象環境を含む明示的承認なしに実行しない
- 文書/Skillのみ: `git diff --check`、Skill validatorなど対象固有の検証を行い、無関係なアプリ検証は省略理由を記録する

失敗を成功扱いにしない。環境変数、ブラウザ、ネットワーク、権限などで実行できない場合は、原因、試した内容、未確認項目を記録する。

## 8. 差分を自己レビューする

1. `git status --short`、`git diff --check`、`git diff` を確認する。
2. `references/self-review-checklist.md` を読み、該当する全項目を確認する。
3. 問題を見つけたら修正し、影響する検証を再実行する。
4. 修正後に差分全体を再レビューする。
5. 要件を満たし、重大な問題と未説明の検証不足がなくなるまでcommitへ進まない。

## 9. コミットする

1. `git diff --name-only` で変更対象を確認する。
2. 自分が変更したパスだけを明示してstageする。`git add .` や無関係な既存変更のstageを避ける。
3. `git diff --cached` を再レビューする。
4. 履歴に明確な規約がなければ、短い命令形の件名を使い、必要に応じて `feat:`、`fix:`、`refactor:`、`test:`、`docs:`、`chore:` を付ける。
5. commit後に `git status --short --branch` を確認する。

## 10. pushとPRを作成する

計画に含まれ、承認された場合だけ実行する。

1. リモートと現在branchを確認する。
2. 認証済みなら作業branchをpushする。
3. `references/pull-request-template.md` を読み、実際の差分と検証結果で本文を埋める。
4. GitHub CLIなど利用可能な手段でPRを作成する。
5. UI変更ではスクリーンショットを添付するか、取得できない理由と手動確認方法を記載する。

権限や認証がない場合は無理に回避せず、未実施作業とユーザーが実行する具体的なコマンドを示す。

## 11. 最終報告する

次を簡潔に報告する。

- 実装した内容と設計判断
- 主要な変更ファイル
- 実行した検証と結果
- 自己レビューで見つけて修正した事項
- commit hash、push先、PR URL
- 未実施項目、既知の制約、必要な手動確認
